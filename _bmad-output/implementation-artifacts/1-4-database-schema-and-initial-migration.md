# Story 1.4: Database Schema & Initial Migration

Status: review

## Story

As a developer building the persistence layer,
I want the `todos` table created with the seam-shape schema (nullable `owner_id`),
so that subsequent stories can read and write through Drizzle against a real Postgres instance and the four-component seam (browser-key → request-context → ownership-check → owner_id) has its persistence anchor in place.

## Acceptance Criteria

Source: `_bmad-output/planning-artifacts/epics.md` § Story 1.4 (lines 288–303).

1. **Given** an initialized project + Postgres reachable per `.env`, **When** I add `drizzle-orm` + `drizzle-kit` + `postgres` (postgres.js) and define `db/schema.ts`, **Then** the `todos` table has columns: `id` (uuid PK, default `gen_random_uuid()`), `description` (varchar, NOT NULL), `completion_status` (boolean, NOT NULL, default `false`), `created_at` (timestamptz, NOT NULL, default `now()`), `owner_id` (uuid, **nullable**).
2. **And** `db/migrations/0001_init.sql` is generated by `drizzle-kit generate` and applied successfully against a fresh Postgres 17 database.
3. **And** index `idx_todos_owner_id_created_at` on `(owner_id, created_at DESC)` exists.
4. **And** Drizzle schema declares column-name aliases so the boundary maps snake_case (DB) ↔ camelCase (TS): `description` → `description`, `completion_status` → `completionStatus`, `created_at` → `createdAt`, `owner_id` → `ownerId`. The TS-side names follow camelCase naming convention from architecture line 273.
5. **And** `db/client.ts` exports a single Drizzle connection (Postgres connection pool initialized once); integration test confirms a SELECT query works against the real DB.
6. **And** **CI migration test (Test 1.4-INT-001)** — TEA amendment M-1: a test (script-runnable now, hooked to CI in Story 2.7) spins up a fresh Postgres 17 container, runs all migrations from `0001_init.sql` onward, asserts schema state — column types match, `owner_id` is nullable, `idx_todos_owner_id_created_at` index is present. *Mitigates DATA-4 (migration failure on deployment, score 6).*

## Dev Notes

### Why this story matters (training-identity context)

Story 1.4 lands the **persistence anchor of the four-component seam** (architecture line 234: "browser-key utility ↔ request-context middleware ↔ ownership-check stub ↔ `owner_id` field"). The nullable `owner_id` is the architectural decision that lets v1 use a per-browser identity proxy *and* lets a future auth module replace the principal source without a schema migration.

Per the anti-flattening rule on seams: the four named seams are not just "good architecture" — they're concrete artifacts the trainee can point at. After Story 1.4, the trainee can run `psql -d todo -c "\d todos"` and *see* the nullable `owner_id` column. That visibility is part of what training identity buys.

### Architectural context

- **DB engine (locked):** Postgres 17, alpine variant for Stories 2.x containers. Architecture line 167: "Decision: Postgres 17 in container."
- **ORM (locked):** Drizzle ORM. Architecture line 172: "Schema-in-TypeScript, type-safe queries that read like SQL, built-in migration tooling. Crossed Prisma in 2025 downloads. SQL-first design is good for trainee transparency. Rejected: Kysely (no migration tool), Prisma (heavier client + binary engine), raw `pg` (no type safety)."
- **Driver (this story's choice):** `postgres.js` (the npm package literally named `postgres`). Architecture line 700: "Drizzle uses `node-postgres` or `postgres.js`" — both are acceptable; this story picks the lighter zero-dep `postgres.js`.
- **Naming conventions (locked):**
  - DB tables, columns, indexes: snake_case lowercase (lines 246–250). `todos`, `description`, `completion_status`, `created_at`, `owner_id`, `idx_todos_owner_id_created_at`.
  - TS variables, functions: camelCase (line 273). Drizzle column-name aliases bridge the two: `description: text("description")`, `completionStatus: boolean("completion_status")`, etc.
  - File names — modules: kebab-case (line 270). DB layer files: `db/schema.ts`, `db/client.ts`, `db/migrations/0001_init.sql` — flat naming, no kebab-case needed for these one-word filenames.
- **Migration tooling (locked):** drizzle-kit. Migrations land as plain SQL files in `db/migrations/`, *trainee-readable directly*. Architecture line 173: "migrations as plain SQL files in `db/migrations/`, trainee-readable directly."
- **Idempotency contract:** Architecture line 191 — `POST /todos` uses `INSERT ... ON CONFLICT (id) DO NOTHING`. Story 1.4's schema must support this — the `id` column being a UUID PK with `gen_random_uuid()` server-side default but **also accepting a client-provided UUID** is what makes idempotency work. Drizzle supports this naturally: if the client provides `id`, the insert uses that value; if not, the DB generates one. **Do not add a CHECK constraint that forbids client-provided IDs.**
- **Db connection pool (locked):** single instance per process. Architecture line 668: "Connection pool initialized once in `db/client.ts`." `postgres.js` manages its own pool internally — the `postgres(connectionString)` call returns a poolable client. Don't manually configure pool size in Story 1.4 (Story 2.3's Zod-validated env config will own that knob).

### LLM-developer guardrails

- **Do not regenerate the migration repeatedly.** `drizzle-kit generate` should be run once. The generated `0001_init.sql` is canonical — the trainee reads it directly. If you generate, then change the schema, then regenerate, you'll create a diff migration (`0002_*.sql`) instead of editing 0001. **For Story 1.4 specifically: the goal is a single clean `0001_init.sql`.** If you need to iterate, delete the entire `db/migrations/` directory and regenerate.
- **Do not commit `.env`.** Only `.env.example`. Verify with `git status` before committing.
- **Do not import `db/client.ts` from anywhere under `app/components/` or `app/lib/`** (other than future `db/client.ts → app/services/`). These are client-bundled; the postgres driver doesn't run in browsers.
- **Do not add a separate `pg` driver as a fallback.** Pick `postgres.js` and stick with it. If something doesn't work, fix the postgres.js usage.
- **Do not add `pgcrypto` extension manually.** `gen_random_uuid()` is built into Postgres 13+ via the bundled `pgcrypto` extension; on `postgres:17-alpine` it's available without `CREATE EXTENSION`. If the migration fails because the function isn't found, then add `CREATE EXTENSION IF NOT EXISTS pgcrypto;` at the very top of `0001_init.sql`. **Verify first** — don't add it preemptively.

**`db/client.ts` exports both `db` (Drizzle instance) and `sql` (raw postgres.js client).** The raw client is exported because the migration assertion test (`db/migrations.test.ts`) needs to issue `information_schema.columns` and `pg_indexes` queries that aren't naturally expressible through the typed Drizzle API. Service-layer code in Story 1.7+ should ONLY use `db`; the `sql` export is a deliberate test-only escape hatch.

**Vitest per-file environment (`// @vitest-environment node`):** required for both DB integration tests because the default jsdom environment doesn't have a usable Node net stack. Documented at the top of both `db/client.test.ts` and `db/migrations.test.ts`.

**The integration tests skip cleanly when `DATABASE_URL` is absent** — `describe.skip` at the top of each file. A contributor without Postgres reachable can still run `pnpm test` and only the 8 unit tests from Story 1.3 will execute. Story 2.7's CI will set `DATABASE_URL` so all tests run.

**.env-handling note for trainees.** `dotenv` is loaded via `import "dotenv/config"` in two places: `drizzle.config.ts` (so `pnpm db:generate` / `pnpm db:migrate` find DATABASE_URL) and the top of each integration test file (so `pnpm test` finds it). Story 2.3 (Zod env validation) will replace this pattern with a typed env loader.
